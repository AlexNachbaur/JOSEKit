# Contributing to JOSEKit

Thanks for your interest in contributing. JOSEKit is young and moving quickly, so this guide is
short: when in doubt, open an issue and ask.

## Getting started

1. Install a **Swift 6.3** toolchain: Xcode 26.5 or later on macOS, a
   [swift.org](https://swift.org/install/) toolchain on Linux or Windows, or the `swift:6.3`
   Docker image, which is what CI uses for Linux.
2. Fork and clone the repository.
3. Build and test from the command line:

   ```sh
   swift build
   swift test
   ```

   On macOS you can also open `Package.swift` in Xcode.

4. To check behaviour against an independent implementation, run the closed-loop interop checks
   against [panva/jose](https://github.com/panva/jose). They need Node:

   ```sh
   ./scripts/interop.sh            # every module
   ./scripts/interop.sh jwe        # one module
   ```

On Linux, building needs zlib's headers (`zlib1g-dev` on Debian and Ubuntu, `zlib-devel` on
Fedora and RHEL), for JWE compression.

## Reporting bugs and requesting features

- Search [existing issues](https://github.com/AlexNachbaur/JOSEKit/issues) first.
- Use the issue templates. A minimal reproduction (the token, the key's public JWK, and the
  observed and expected result) makes bugs much faster to fix. Generate throwaway keys for it;
  never paste real private keys or live tokens.
- For anything security-sensitive, **do not open a public issue**. See [SECURITY.md](SECURITY.md).

## Design

Settled design decisions are in [DESIGN.md](DESIGN.md): section 2 is the safety model, and the
decision tables at the end record what was chosen and why. Changes to the public API, or
anything that touches those decisions, should start as an issue describing the problem and the
proposed approach before code is written. What is deliberately deferred or left out is in
[TODO.md](TODO.md).

## Code style

Formatting is enforced by `swift-format` with the checked-in [.swift-format](.swift-format)
configuration. CI fails on lint violations, so run this before pushing:

```sh
swift format lint --strict --recursive Sources Tests Package.swift
```

(`swift format --in-place --recursive Sources Tests Package.swift` applies the fixes.)

Beyond formatting, the project follows these rules:

- **120-character lines, 4-space indentation.**
- **Swift 6 with strict concurrency, and typed throws.** No `DispatchQueue`.
- **No `try?`, `try!`, force unwraps (`!`) or force casts (`as!`).**
- **No static-only types** (DESIGN.md D24): no caseless enums or private-`init` structs used as
  namespaces. Behaviour lives on instances, parsing in initialisers, and small utilities in
  extensions.
- **No nested ternaries.**
- **Comments describe what the code does now.** A comment must not claim behaviour the code
  lacks.
- **Stay cross-platform.** JOSEKit supports macOS, iOS, Linux, Windows and Android. CI builds
  and tests on all of them and must pass on all of them.

## Tests

- **Every guard has a test that fails when the guard is removed.** Before opening a pull
  request, break each new check by hand (delete it, or invert it), run the tests, and confirm
  one goes red. Then restore it.
- **Expected values come from an independent implementation, not from the code under test.**
  Fixtures in `Tests/*/Fixtures` are generated by the scripts in `interop/` from panva/jose and
  OpenSSL, and are not edited by hand. Rerun the generator when a fixture needs to change.
- Shared test helpers live in the `TestSupport` target.

## Pull requests

- Branch from `main`, and keep each pull request to one change.
- Add or update tests for any behavioural change.
- Update the documentation (README, `Documentation/`, DESIGN.md, doc comments) when the public
  API changes.
- Make sure lint and `swift test` pass locally. If the change touches what tokens look like on
  the wire, run `./scripts/interop.sh` too.

Until the first release, and while the project is pre-1.0, the public API may change without
deprecation; call out breaking changes in the pull request description.
